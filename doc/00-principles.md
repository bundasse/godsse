# 00. 프로젝트 대원칙 (최우선)

> 이 문서는 `godsse` 프로젝트에서 **가장 먼저 확인해야 하는 문서**입니다.
> 다른 문서·관행·지시와 충돌할 경우 **이 문서가 우선**합니다.

## 이 원칙이 어디에 적용되나

| 위치                             | 역할                                                             |
| -------------------------------- | ---------------------------------------------------------------- |
| `.clinerules/00-principles.md`   | AI 도구(Cline)가 **작업 시작 시 자동으로 읽는** 요약·명령형 규칙 |
| `AGENTS.md` (프로젝트 루트)      | `AGENTS.md` 를 지원하는 다른 도구(Cursor, Codex 등)용 공통 지침  |
| `doc/00-principles.md` (이 문서) | 사람이 읽는 **상세 해설판** + 실천 방법·템플릿·체크리스트        |

세 문서의 원칙은 동일하며, 내용이 바뀌면 **세 곳을 함께 갱신**합니다.

## 원칙 1. 언어: 한국어 우선

**규칙**

- 사용자와의 모든 보고·질문·설명·요약은 **한국어**로 작성한다.
- 한국어로 적확한(정확하고 적절한) 설명이 불가능한 경우에만 영어로 설명하고, 이때는 영어 원어를 함께 표기한다.
- 코드·식별자·명령어·에러 메시지·파일 경로는 원문을 유지한다(번역하지 않는다).

**실천 예**

- 좋은 예: "이 설정은 `CorsConfig` 에서 오리진(origin)을 제한합니다."
- 좋은 예: "CORS(Cross-Origin Resource Sharing, 다른 출처 간 자원 공유) 설정입니다."
- 피해야 할 예: 모든 내용을 영어로만 서술하거나, 한국어와 영어를 뒤섞어 문장을 불완전하게 만드는 것

**예외**

- 사용자가 영어 설명을 요청한 경우
- 코드/로그/명령 출력 등 원문 인용이 필요한 경우

## 원칙 2. 계획 → 승인 → 실행 (무단 수정 금지)

**규칙**

1. 지시를 받으면 **곧바로 수정하지 않는다.** 먼저 계획을 정리해 보고한다.
2. 사용자가 **명시적으로 승인한 뒤에만** 파일 생성·수정·삭제 및 상태를 바꾸는 명령을 실행한다.
3. 조사·읽기·검색(git status, 파일 읽기, 검색 등)처럼 **상태를 바꾸지 않는 작업은 승인 없이** 가능하다.
4. 승인 범위를 벗어나는 추가 변경이 필요하면 **다시 계획을 보고하고 승인**받는다.
5. 실수로 승인 없이 실행했음을 인지하면 **즉시 중단 → 되돌림 → 보고**한다.

**계획 보고 템플릿 (이 형식을 사용)**

```
## 계획
1. 요구사항 요약
   - (무엇을 왜 하는가)
2. 변경할 파일
   - 신규: 경로/파일명 — 무엇을 담는가
   - 수정: 경로/파일명 — 어느 부분을 어떻게 바꾸는가
3. 검증 방법
   - 실행할 명령 / 확인할 결과 (예: npm run lint, npm run build, .\mvnw.cmd test)
4. 리스크·대안
   - 예상 부작용, 되돌리는 방법, 다른 선택지
```

**승인 기준**

- "진행해 주세요", "OK", "승인" 처럼 **명시적인 표현**이 있어야 실행한다.
- "좋아 보이네요", "그렇군요" 같은 감상 표현은 승인으로 해석하지 않는다.
- 승인 후에도 계획에 없던 변경이 필요해지면 멈추고 재보고한다.

**왜 이렇게 하나**

- 되돌리기 어려운 변경(파일 삭제, 대량 수정, 의존성 변경)을 사전에 차단하고, 사용자가 프로젝트 진행 방향을 통제할 수 있게 하기 위함이다.

## 원칙 3. 사용자 배경을 고려한 설명

**사용자 프로필 (모든 설명의 전제)**

- Vue 프론트엔드 개발자 (Vue 3 + Vite 경험 있음)
- React 는 조금 알고 있음
- **백엔드 · Java · Spring Boot · 컴퓨터공학 지식은 매우 기초 수준**

**설명 순서 (백엔드 관련 내용은 반드시 이 순서로)**

1. **전제 개념** — 이걸 이해하려면 먼저 알아야 하는 것부터
2. **왜 필요한가** — 없으면 어떤 문제가 생기는가
3. **이 프로젝트에서는** — `godsse` 의 어느 파일/설정에서 쓰이는가 (경로 표기)
4. **예제** — 실제 프로젝트 코드 인용

**프론트엔드(Vue/JS) 비유 예시**

| 백엔드 개념               | 프론트엔드 비유                                                    |
| ------------------------- | ------------------------------------------------------------------ |
| 빈(Bean)                  | 필요할 때 주입받아 쓰는 "등록된 컴포넌트/인스턴스" 같은 것         |
| DI(의존성 주입)           | props 로 넘겨받듯, 생성자로 필요한 객체를 받아 쓰는 방식           |
| 컨트롤러(Controller)      | vue-router 의 라우트 + 페이지 컴포넌트가 요청을 받아 처리하는 구조 |
| DTO                       | API 응답용 TypeScript `interface` 처럼 데이터 모양을 정의한 것     |
| Bean Validation(`@Valid`) | vee-validate 같은 폼 검증을 서버 쪽에서 선언형으로 하는 것         |
| `application.properties`  | `.env` + `vite.config.js` 같은 프로젝트 설정 파일                  |
| Spring Boot               | Nuxt 처럼 "프레임워크가 구조·실행·설정을 잡아주는" 도구            |

**용어 표기 규칙**

- 처음 등장할 때 `한국어(영어 원어)` 로 쓰고 **한 줄 정의**를 붙인다.
  - 예: "빈(Bean): 스프링이 대신 만들어서 관리해 주는 객체"
- 한 번에 여러 개념을 나열하지 않는다. 필요한 만큼만 단계적으로 설명한다.
- "당연히 아시겠지만", "쉽게 말해" 처럼 상대 지식을 전제하는 표현은 쓰지 않는다.

**실천 예**

- 좋은 예: "지금 `CorsConfig` 에 `@Configuration` 이 붙어 있는데, 이 애노테이션은 '이 클래스는 설정 클래스야'라고
  스프링에게 알려주는 표시입니다. Vue 로 치면 플러그인 등록 파일과 비슷합니다."
- 피해야 할 예: "컴포넌트 스캔으로 등록된 빈이 WebMvcConfigurer 로 주입되어 CORS 매핑이 적용됩니다." (설명 없이 용어 나열)

## 원칙 4. 학습 자료화 + 읽기 요청

**규칙**

- 백엔드 · Java · Spring · 컴퓨터공학 관련 내용이 나오면 `doc/study/` 아래에 **학습 노트(markdown)** 로 정리한다.
- 정리한 직후 **"지금 이 파일을 읽어보세요"라고 경로와 함께 명시적으로 요청**한다. (읽는 데 걸리는 예상 시간도 함께 안내)
- 노트 형식: **개념 → 왜 필요한가 → 이 프로젝트에서는 → 예제 코드 → 확인 문제(선택)**
- 노트를 만들면 `doc/study/README.md` 의 "노트 목록" 표에도 등록한다.
- 노트는 **10분 내외** 분량으로 짧게 유지하고, 프론트엔드 비유를 반드시 1개 이상 포함한다.

**노트를 만드는 시점(트리거)**

- 새로운 Java 문법·키워드·자료형이 등장했을 때 (예: `record`, `var`, 제네릭)
- Spring 애노테이션·개념이 등장했을 때 (예: `@RestController`, DI, 빈)
- 빌드·실행·테스트 도구가 등장했을 때 (예: Maven Wrapper, JUnit, MockMvc)
- 에러의 원인과 해결 과정을 설명할 때
- 구조적 결정(계층 분리, 예외 처리 방식 등)을 할 때

**요청 문구 예시**

```
📘 학습 노트를 만들었습니다: doc/study/03-spring-boot-structure.md
지금 읽어보세요. (약 7분)
읽고 궁금한 점을 알려주시면 그 부분을 더 깊게 정리한 노트를 추가하겠습니다.
```

## 원칙 위반 시 대응 / 적용 범위

**위반을 인지했을 때**

1. 즉시 작업을 멈추고 사실을 알린다.
2. 변경한 내용을 요약해 보고하고(어떤 파일의 어느 부분), 원복 여부를 함께 제안한다.
3. 사용자 판단에 따라 원복하거나 유지한다.

**원칙 2의 예외 (승인 없이 가능한 것)**

- 읽기·검색·조회 등 상태를 바꾸지 않는 모든 작업
- 사용자가 **명시적으로 "승인 없이 진행해도 된다"고 위임한 범위** (예: "테스트 실행은 물어보지 말고 해")
  - 이 경우에도 위임 범위를 벗어나면 다시 승인을 받는다.

**원칙 변경 방법**

- 원칙은 사용자가 지시할 때만 변경한다.
- 변경 시 **세 파일(`.clinerules/00-principles.md`, `AGENTS.md`, `doc/00-principles.md`)을 동시에 갱신**하고,
  아래 변경 이력에 기록한다.
